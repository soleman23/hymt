## 2. Current-state architecture (verified 2026-10-02 against HEAD 5f547a7e and production)

### Page assembly
- Every `/experiences/<slug>/` page is a two-file pair: `src/pages/experiences/<slug>/index.astro` (props: title, description, name, hero) wrapping `src/content-pages/experiences__<slug>.html` (body sections, imported `?raw`, rendered through `<Fragment set:html>`). The wrapper imports `ExperienceLayout.astro`, which owns the breadcrumb (hardcoded three-crumb trail Home › Experiences › Name), the hero, the JSON-LD (BreadcrumbList + WebPage + Service + FAQPage parsed from the slot HTML by `extractFaq`) and the og:image lookup (`OG_CROPS[hero.image]`).
- Every `/destinations/<slug>/` page is the same shape on `DestinationLayout.astro`, with one extra prop, `region: {label, href}`, which adds the fourth crumb (Home › Destinations › Region › Name) on the 59 country pages and is omitted on the 9 regional hubs. Schema is BreadcrumbList + WebPage + TouristDestination + FAQPage. The hero stat rail must carry "Best Season" and "Best For" (verifier `hero-stat-rail`).
- The hubs `/experiences/` and `/destinations/` are plain `Base.astro` pages with hand-written card HTML and a CollectionPage ItemList built from a depth-1 glob of child `index.astro` files. A nested route such as `/experiences/<parent>/<child>/` would NOT join either ItemList and would NOT change the "12 trip types" count that `public/llms.txt` states and the verifier enforces (`sectionCount` reads depth-1 directories only).
- `Base.astro` derives canonical, og:url and all JSON-LD URLs from `astro.config.mjs` `site`. The canonical never carries a query string, so `?type=` prefills on `/plan-your-trip/` are safe for the form and invisible to search.
- Styling: `section-shared.css` (breadcrumb, buttons, intro, seasons, read-more, FAQ, cost-range) imported first, then `experience.css` or `destination.css`. No per-page CSS is allowed under the three templated directories (verifier `shared-template`).

### The tiles
- 12 experience partials carry 78 `.exp-card` anchors in an `.exp-cards.exp-cards--photo` grid under `<section class="exp-cards-section" id="destinations">`: 6 on ten pages, 9 on `family-travel` and `food-wine-travel`. Each card is `<a class="exp-card" href="/plan-your-trip/">` wrapping an `<img class="exp-card__img">`, a region eyebrow, a name, a description, 2–3 tags and an "Explore →" arrow. Because the card IS the anchor, nothing inside it may be a link (verifier `nested-card-anchor`).
- The same 12 partials carry 48 `.event-card` "Trips We Plan Often" itinerary cards, each with `<a class="event-cta" href="/plan-your-trip/">Plan This Trip</a>`.
- All 126 link to `/plan-your-trip/` in source, in `dist/`, and on production (all 12 pages fetched from www.hymtravel.com on 2026-10-02; the production sitemap's 122 URLs are identical to `dist/sitemap-0.xml`).
- The pattern is wider than the experience pages: 67 destination pages carry 386 `.place-card` anchors, 330 of which also point at `/plan-your-trip/` (the 56 exceptions are the nine hubs' child cards, which link to real destination pages: the precedent this plan generalises), and 248 `.itin-cta` buttons point at the form. Out of scope here, but the data model below is sized so the same mechanism can serve them later.

### Reverse linking today
- Only 3 of 68 destination pages link to any experience page (costa-rica, dominican-republic, zambia-victoria-falls). Experience pages link to destination pages mostly from seasons copy and FAQ answers; no tile links anywhere.
- Each destination page has exactly one stable anchor, `id="places"` (the places-section grid); `/destinations/maldives/` is the one page with `id="experiences"` (a `dest-exp-section` of six non-linking experience cards) and a different section set (dest-intro, seasons, experiences, stay, practical, related, split CTA) — it is 1,765 words against the 3,500 ceiling and is the natural prototype for an "experiences in this destination" module.

### Existing data layers (what already drives content from data)
- `tools/cost-ranges-data.mjs` → `tools/p3-8-cost-insert.mjs`: a keyed data file plus an idempotent insert script that rewrites a marked section in each partial. This is the repo's established pattern for data-driven content without a component refactor.
- `tools/p3-6-related-destinations.mjs`: a slug → (name, region, hub, hero) map used once to write the `related-section` into 59 pages (idempotent on `data-p3-6`).
- `tools/itin-brief.json`, `images-b64/MANIFEST.json`, `src/lib/og-crops.ts` (generated by `tools/make-og-crops.mjs`): image data.
- There is NO tile-to-page map. Tile targets are 126 literal `href` attributes.

### Build and verification gates that constrain this work
- `npm run build` = Node preflight → lockfile restore → `astro build` → sitemap reflow → comment strip → image restore → responsive images → check fixtures → `tools/verify-deployment.mjs` (63 named checks). Relevant ones: `shared-template`, `nested-card-anchor`, `photo-grid`, `internal-links` (every same-site href must resolve in `dist/`, so a mistyped tile target already fails the build), `internal-link-floor` (≥2 journal links on every destination/experience page), `page-length` (3,500-word ceiling on 4-crumb destination pages), `head-baseline` (any title/description change needs `--update-baseline` in its own commit), `schema-required` (by path prefix: `/experiences/**` must emit Service, `/destinations/**` TouristDestination), `sitemap-parity`, `llms-txt` counts, `img-attrs`, `img-ratio`, `missing-asset`, `remote-coverage`.
- A build is deterministic: an unchanged tree rebuilds `dist/` byte-identical. That is the regression test for any layout change: if no page opts into a new prop, `git diff --stat dist/` must be empty apart from the pages deliberately changed.
- Sitemap `lastmod` comes from git history per page's own two source files, so a tile-link edit moves only that experience page's date.
- Word headroom (body words vs 3,500) on country pages ranges from 62 (arctic-norway) to 2,135 (napa-sonoma); 27 pages have under 200 words of headroom. Any enhancement to those pages must be a short module, not a section.
